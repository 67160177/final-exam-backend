## เหตุผล

### wk09
1. **ก** Unit Test เร็วและชี้จุดผิดได้แม่น จึงควรมีมากที่สุด ส่วน E2E ช้าและเปราะบาง จึงควรมีน้อยที่สุด (wk09 1.2)
2. **ค** Branch Coverage นับว่าทดสอบครบทุกทางของเงื่อนไขหรือไม่ if/else มี 2 ทาง แต่ทดสอบไปทางเดียว (wk09 5.1)
3. **ง** `mockRejectedValueOnce` ทำให้ Promise ถูก reject หนึ่งครั้ง ใช้จำลอง DB error (wk09-lab 2.5)
4. **ข** Promise ต้องใช้ `rejects` และต้อง `await` ด้วย ถ้าใช้ `toThrow` ตรง ๆ จะใช้ได้กับฟังก์ชันแบบ sync เท่านั้น (wk09 2.4)
5. **ก** ล้างสถานะของ mock เพื่อให้แต่ละ test เป็นอิสระต่อกัน (test isolation) (wk09-lab 2.5)

### wk10
6. **ง** ส่วนหลักคือ `info`, `servers`, `paths`, `components`
7. **ข** ผู้เรียกใช้ต้องรู้รูปแบบ error ล่วงหน้าเพื่อเขียนโค้ดรับมือ (wk10 2.4)
8. **ค** Environment Variable ทำให้ request อื่นใช้ค่าต่อได้ (wk10 4.3-4.4)
9. **ก** เอกสารคือสัญญาระหว่างทีม ถ้าไม่ตรงกับการทำงานจริงเรียกว่า contract mismatch (wk10 5.1)
10. **ง** รูปแบบ error ที่ไม่สม่ำเสมอทำให้ผู้ใช้ API ต้องเขียนโค้ดแยกรับมือทีละ endpoint

13. **ก** Webhook อาจถูกส่งซ้ำได้ จึงต้องออกแบบให้ idempotent (wk11 สรุปข้อ 6)
14. **ง** HMAC ต้องใช้ secret ไม่รู้ secret ก็คำนวณ signature ที่ถูกต้องไม่ได้ (wk11 คำถามท้ายบทข้อ 10)
