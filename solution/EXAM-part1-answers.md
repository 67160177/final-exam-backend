## เหตุผล

### wk09
1. **ข** Supertest ต้อง `require("./app")` มาใช้ตรง ๆ ถ้า `listen()` หรือ `connectRedis()` อยู่ในไฟล์เดียวกัน เทสต์จะเปิดพอร์ตหรือต่อ Redis จริงทุกครั้งแล้วอาจค้างหรือ fail (wk09 3.2 และ wk09-lab 2.2)
2. **ค** `toEqual` เทียบเนื้อหาของ object แบบ deep ส่วน `toBe` ใช้ `===` ซึ่ง object สองตัวที่สร้างแยกกันจะไม่เท่ากันเสมอ
3. **ง** เทสต์ที่เรียกฟังก์ชันโดยไม่มี `expect` ก็ทำให้ Coverage ขึ้นได้ (wk09 5.3)
4. **ก** เทสต์ต้องเป็นอิสระต่อกัน ข้อมูลค้างจากการรันครั้งก่อนทำให้ผลไม่คงที่ (wk09 3.4 และคำถามท้ายบทข้อ 8)
5. **ค** ถ้าต้องการพิสูจน์ว่า query ตรงกับ schema จริง ต้องเป็น Integration Test กับฐานข้อมูลทดสอบ เพราะ mock จะคืนค่าตามที่เรากำหนดเสมอ (wk09 4.4)

### wk10
6. **ข** นิยาม schema ไว้ที่เดียว (single source of truth) แล้วใช้ซ้ำทุก endpoint
7. **ข** เอกสารอยู่ใน repository เดียวกับโค้ดและ deploy ไปพร้อมกัน ส่วนตัวเลือก ก ผิดเพราะ Swagger UI แค่แสดงผลไฟล์ spec ไม่ได้อ่าน route ให้เอง
8. **ค** Environment Variable ทำให้สลับสภาพแวดล้อมได้โดยไม่ต้องแก้ทีละ request
9. **ข** Newman ทดสอบระดับ HTTP กับเซิร์ฟเวอร์ที่รันอยู่ ส่วน Supertest ทดสอบระดับโค้ด
10. **ค** ใช้ spec เป็นสัญญาก่อนลงมือเขียน ทั้งสองทีมจึงทำงานคู่ขนานกันได้

### wk11
11. **ง** 400 เป็น permanent failure ส่งซ้ำกี่ครั้งก็ผิดเหมือนเดิม ส่วน 503, 429 และ network error เป็น transient failure
12. **ข** `error.response` มีค่าก็ต่อเมื่อปลายทางตอบกลับมาด้วย status ที่ไม่ใช่ 2xx ถ้าไม่มีค่าแปลว่าไม่ได้รับ response เลย
13. **ค** เรียก 3 ครั้ง ครั้งละ 2 วินาที รวม 6 วินาที บวก backoff 1 + 2 = 3 วินาที รวม 9 วินาที (สูตร `timeout × จำนวนครั้งที่เรียก + ผลรวม backoff` จาก wk11 4.3)
14. **ก** Jitter สุ่มเวลารอเพิ่ม ทำให้ client แต่ละตัวไม่ retry พร้อมกันพอดี
15. **ค** `===` หยุดเทียบทันทีที่เจอตัวที่ต่าง ทำให้เวลาตอบสนองรั่วข้อมูลออกไป ส่วน `timingSafeEqual` ใช้เวลาเท่ากันทุกครั้ง

### wk12
16. **ก** เป็นกฎแบบมีเงื่อนไขที่ต้องแจ้ง error ได้หลายจุดพร้อม `path` ของแต่ละ field ส่วน `.refine()` คืน error ได้ครั้งละหนึ่งรายการ
17. **ค** Rate Limiting ตัดทันทีด้วย 429 (ใช้ `express-rate-limit`) ส่วน Throttling หน่วงเวลา (ใช้ `express-slow-down`)
18. **ข** ถ้าไม่ตั้ง trust proxy ค่า `req.ip` ที่เห็นคือ IP ของ proxy ผู้ใช้ทุกคนจึงได้ key เดียวกัน วิธีแก้คือ `app.set("trust proxy", 1)`
19. **ง** store เริ่มต้นเก็บตัวนับใน memory ของแต่ละ process 4 process × 5 จึงได้ 20 ครั้ง วิธีแก้คือใช้ `rate-limit-redis`
20. **ข** ตัวเลือก ค ผิดเพราะผู้ใช้ที่ยังไม่ login จะ fallback ไปใช้ IP จึงยังถูกนับรวมกันอยู่ ส่วนตัวเลือก ง ผิดเพราะ `ipKeyGenerator` ช่วย normalize ที่อยู่ IPv6

### wk13
21. **ข** การแบ่งตามชั้นทางเทคนิคทำให้ทุก request ต้องเรียกข้ามบริการ ควรแบ่งตาม Bounded Context ทางธุรกิจแทน
22. **ง** Gateway ไม่ใช่ที่เก็บข้อมูล แต่ละบริการควรเป็นเจ้าของข้อมูลของตัวเอง (data ownership)
23. **ก** งานที่ไม่ต้องการผลทันทีควรใช้ Asynchronous
24. **ค** สถานะ Closed ปล่อย request ตามปกติ, Open ปฏิเสธทันที, Half-Open ลองส่ง request ทดสอบจำนวนน้อย
25. **ข** เริ่มจาก Modular Monolith ก่อน เพื่อเลี่ยงต้นทุน operational overhead และปัญหา Distributed Monolith

### wk14
26. **ค** column แบบ `NOT NULL` ที่ไม่มี default ทำให้แถวเดิมไม่มีค่าที่ถูกต้อง migration อาจล้มหรือเกิดค่าที่ไม่ตั้งใจ ส่วน `down` ทำให้มีแผนย้อนกลับ
27. **ก** `migrate:rollback` ย้อนกลับ batch ล่าสุดด้วยฟังก์ชัน `down` ไม่ได้ restore จาก backup ซึ่งเป็นแผนสำรองอีกขั้นสำหรับ migration ที่ย้อนกลับไม่ได้
28. **ง** ขั้นตอนคือ Expand → Migrate (เขียนสองที่และ backfill) → Contract
29. **ข** Round Robin ไม่ได้ผูกผู้ใช้กับเครื่องเดิม (IP Hash จึงจะผูก) แนวทางที่ถูกคือออกแบบแอปให้ stateless
30. **ค** 5 instance × 10 = 50 connection เกินเพดาน 40 (wk14 3.4)
